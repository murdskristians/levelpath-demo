# Intent: Tenancy and RLS foundation

<!-- Drafted by Claude from KICKOFF Phase 2; Chris decided the query layer, migrations, auth stub and key type. -->

## Problem

The demo is a multi-tenant purchase-request system, but it has no database schema, no notion of a tenant and no login. Without them there is nothing to protect, and the one hard requirement (tenant A can never read or write tenant B's data) is not yet enforced or proven.

## Outcome

Every tenant-owned table lives in Postgres with row-level security forced on, the API only ever reaches data through a transaction that sets the current tenant, and an automated test suite proves tenant A cannot select, update or delete tenant B's rows, even with a crafted ID.

## Users and roles

- **Tenants** (companies), **users** (belong to one tenant, role `requester` or `approver`), **suppliers** (per tenant), **purchase requests** (draft → submitted → approved | rejected) and **approvals** (who, when, comment).
- A stub login stands in for real auth: seeded users, picked by a header or a dev login. Real authentication is out of scope, and the docs say so.

## Constraints

- **Decided: Kysely** as the query layer (typed SQL builder, explicit transactions). Chosen over Drizzle, TypeORM and Prisma; see `docs/LEARNING.md`.
- RLS is enabled **and forced** on every tenant table. The app connects as a **non-owner** role; migrations run as the owner; policies read `current_setting('app.tenant_id', true)`.
- Every database operation runs in a transaction that starts with `SET LOCAL app.tenant_id`, so a pooled connection can never carry one tenant's context into the next request. The docs explain this risk and how the design avoids it.
- Tests use the real database and real policies. Nothing about the database or RLS is mocked.
- Keep it small: only the five tables above, no features beyond what the tests need.

## Out of scope

- The purchase-request create, submit and approve screens and endpoints (Phase 3).
- The LLM suggestion feature (Phase 4).
- Real authentication, password handling, user management.
- CI changes (Phase 5).

## Open questions

Each gets options and a recommendation in the plan; Chris decides.

None. Chris decided:

- **Migrations:** plain numbered `.sql` files, applied as the owner by a small script that records what ran.
- **Auth stub:** an `X-User-Id` header, resolved against seeded users to get tenant and role.
- **Primary keys:** UUIDs generated by Postgres (`gen_random_uuid()`).
