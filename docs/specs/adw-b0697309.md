# Edit a draft purchase request before submitting it

> Issue #32: Intent: Edit a draft purchase request before submitting it · Type: feature · Intent: issue #32 body (no intent file)

## Summary

- New route `PUT /purchase-requests/:id`: the requester who created a request replaces its six form fields while it is a `draft`. Status, requester, tenant and id never change.
- Anyone else (an approver, another user of the same company, another company, an unknown or non-UUID id) gets the same `404` as for a request they can't see. A request that is no longer a draft gets `409`, the way a second submit does. A refused edit writes nothing.
- The body is the shared `createPurchaseRequestSchema` (exported again as `updatePurchaseRequestSchema`), so create and edit validate the same way in the API and in the web form.
- In "My requests", each draft gets an **Edit** button next to **Submit**. It opens the same form, filled in, in the place of the new-request form. **Save changes** keeps it a draft and refreshes the list. **Cancel** changes nothing. **Suggest fields** works as it does when creating.
- No migration: the `UPDATE` grant and the `tenant_isolation` policy on `purchase_requests` already cover it.

## Context

- **API routes:** `apps/api/src/purchase-requests/purchase-requests.controller.ts` has `GET mine`, `GET to-decide`, `POST /`, `POST :id/submit` and `POST :id/decision`. Nothing changes a request's fields after create. Bodies are parsed by `ZodValidationPipe` (`apps/api/src/validation/zod-validation.pipe.ts`) on the `@Body()` parameter, so a bad body is a `400` before the service runs.
- **API logic:** `apps/api/src/purchase-requests/purchase-requests.service.ts`.
  - `create` inserts inside `withTenant` and maps a key violation (`isKeyViolation`, `apps/api/src/db/pg-errors.ts`) to `404`. That is how an unknown or other-company supplier is refused: the composite FK `(tenant_id, supplier_id)` in `db/migrations/0003_purchase_requests.sql:28`.
  - `submit` is the pattern to copy. It checks `isUuid` (404), reads the row filtered on `requester_id = user.userId` (404 when missing), refuses a non-draft with `409 'only a draft can be submitted'`, then runs a conditional `UPDATE … WHERE status = 'draft'` and sets `updated_at = now()`.
  - `readBack` builds the response through `selectPurchaseRequests` and `toPurchaseRequest` (`purchase-request.query.ts`).
- **Database:** `purchase_requests` has RLS enabled and forced, with the `tenant_isolation` policy for every command (`0003:31-35`). `{{app_role}}` has `SELECT, INSERT, UPDATE, DELETE` on it (`0003:37`). `description` and `category` come from `0005_purchase_request_description_category.sql`. `updated_at` has no trigger: the code sets it. `db/seed.sql` inserts with `ON CONFLICT (id) DO NOTHING`, so re-seeding does not undo an edit to a seeded row.
- **Shared contract:** `packages/shared/src/purchase-requests.ts`. `createPurchaseRequestSchema` is strict, and it defaults `currency` to `EUR` and `description` to `''`. `purchaseRequestSchema` is the response shape. The contract document is `docs/specs/purchase-requests-contract.md`.
- **Web:**
  - `apps/web/src/api.ts`: `call()` only types `'GET' | 'POST'`.
  - `apps/web/src/App.tsx`: one boolean, `formOpen`, shows `NewRequestForm` above `RequestList`, and `create` closes the form and re-fetches `mine`.
  - `apps/web/src/components/NewRequestForm.tsx`: starts every field empty, is named `New request` and submits with `Create request`.
  - `apps/web/src/components/RequestList.tsx`: shows `Submit` (`aria-label="Submit <title>"`) only on drafts.
  - `apps/web/src/money.ts`: `centsToAmountText` turns cents back into the form's amount text.
- **Tests:** API specs use real HTTP (`startApp`), a raw owner connection (`ownerClient`), `SEED`, `seededRequestsSnapshot` and `deleteRowsTestsCreated` (`apps/api/test/helpers.ts`). The model to follow is `submit.spec.ts`. Web tests use `mockFetch` and the builders in `apps/web/src/test/fixtures.ts`, in `apps/web/src/App.test.tsx`.

## Requirements

1. `PUT /purchase-requests/:id` exists, behind the global `AuthGuard` (no `@Public()`, no `ApproverGuard`). Its body is validated with `updatePurchaseRequestSchema` from `packages/shared`, which is the same schema as `createPurchaseRequestSchema`: the same six fields, the same rules and defaults, strict.
2. On success it sets `title`, `amount_cents`, `currency`, `supplier_id`, `category`, `description` and `updated_at = now()` on the row, and answers `200` with the `PurchaseRequest`. Its `status` stays `draft`, and its `id`, `requester` and `createdAt` are unchanged. It never sets `status`, `tenant_id`, `requester_id`, `id` or `created_at`.
3. Only the user who created the request may edit it, whatever their role. Anyone else gets `404 {"message":"Not Found","statusCode":404}`, the same body as for an unknown id or a non-UUID id. This covers an approver of the same company, another user of the same company, and anyone in another company, including with a crafted id.
4. The creator editing a request that is `submitted`, `approved` or `rejected` gets `409` with the message `only a draft can be edited`. The `UPDATE` is conditional on `status = 'draft'` and `requester_id = <caller>`, so an edit racing a submit can't change a submitted request: no row back is also a `409`.
5. An invalid body gets `400` with `issues`, exactly as on create: an extra key such as `id`, `tenantId`, `requesterId` or `status`, an empty title, an amount over the cap or fractional, a non-UUID `supplierId`, no category or an unknown one, a description over 2000 characters, or no body at all.
6. A `supplierId` the caller's company doesn't have (another company's supplier, or an unknown one) gets the same `404` as create gives.
7. Every refused edit (rules 3 to 6, and `401` without `X-User-Id`) leaves the row exactly as it was: every field and `updated_at`.
8. All reads and writes go through `DatabaseService.withTenant(user.tenantId, …)`. The tenant and the user come from `@CurrentUser()`.
9. `docs/specs/purchase-requests-contract.md` documents the route (its table row, and `UpdatePurchaseRequest` under Shapes). `docs/LEARNING.md` gets one entry on the edit route.
10. The web API client has `updateRequest(id, input)`, which sends `PUT /api/purchase-requests/<id>` with `X-User-Id` and parses the reply with `purchaseRequestSchema`.
11. In "My requests", every `draft` has a button with visible text `Edit` and accessible name `Edit <title>`, next to its Submit button. Requests in any other status have no Edit button.
12. Edit opens the same form component in the same place as the new-request form (above the list), named `Edit request`, with every field filled from the draft: Description, Title, Category, Amount (as `centsToAmountText` gives it, for example `1250.00`), Currency and Supplier. Title has the focus. Only one form is open at a time: while it is open, the New request button is hidden; clicking Edit on another draft shows that draft's values.
13. The edit form's submit button is `Save changes`. It validates with the shared schema, exactly as create does: the same errors next to the same fields, and nothing is sent when a field is invalid. On success it sends all six fields, closes the form and re-fetches "My requests", which shows the new values and still the `Draft` badge. On an API error (for example `409`), the existing error alert shows the message and the form stays open with the user's values.
14. `Cancel` closes the edit form, sends nothing and leaves the list as it was.
15. `Suggest fields` in the edit form calls `POST /purchase-requests/suggestion` and fills the fields as it does in the create form. Save then sends the filled values with `PUT`.
16. The create form is unchanged: it is still named `New request`, its button is still `Create request`, and it starts empty with currency `EUR`. Every existing test passes unchanged.
17. New tests:
    - `apps/api/src/purchase-requests/update.spec.ts` covers rules 2 to 7 and the seed check.
    - `apps/web/src/App.test.tsx` gets a `describe('edit a draft')` block covering rules 11 to 15.

## Tenant isolation and security

- **RLS:** the read and the `UPDATE` both run inside `withTenant(user.tenantId, …)`, as the non-owner app role. The `tenant_isolation` policy hides other tenants' rows, so a crafted Globex id from an Acme caller matches nothing and gets `404`. Its `WITH CHECK` also stops a row from moving to another tenant. `tenant_id` is never in the `set`. Acceptance criterion 3 proves this with a crafted id, checking the Globex row in an owner query.
- **Ownership:** both the read and the `UPDATE` filter on `requester_id = user.userId` from `@CurrentUser()`. The id comes from the path, and the tenant and user never come from the body or the URL. Another user of the same company, approvers included, sees `404`, never `403`, so the response doesn't reveal that the draft exists.
- **Supplier across tenants:** the composite FK `(tenant_id, supplier_id) → suppliers` rejects another company's supplier on `UPDATE`. The service maps the key violation to the same `404` as create, so the answer doesn't reveal that the key exists. The transaction rolls back.
- **Input:** the strict shared schema rejects `id`, `tenantId`, `requesterId`, `status` and any unknown key. The query uses only Kysely's builder, with no raw SQL from input. `X-User-Id` is still the dev stub, not authentication.
- **Order of answers:** the guard, then the body pipe, then the id lookup. A non-owner sending an invalid body gets `400`, which depends only on the body, so it reveals nothing about the id.
- **No PII in logs:** the route logs nothing new.

## Out of scope

- Deleting or discarding a draft. An edit history or audit trail: only `updated_at` changes. Conflict checks between two open forms: the last save wins.
- Editing a submitted, approved or rejected request, or resubmitting a rejected one.
- Any migration, grant or policy change. Any change to `db/seed.sql`.
- A `PATCH` with partial updates, or a separate update schema with different rules.
- Changing how Submit, create or Suggest fields behave, or the create form's names and labels.
- Saving and submitting in one click.
- Editing the request inline in the list, or opening a modal.

## Assumptions

- **`PUT`, a full replacement, with the create schema.** The intake asks for "every field the create form has, with the same validation", and the form always sends all six fields. So a left-out `currency` or `description` takes the create default (`EUR`, `''`), and the client knows this from the contract.
- **"The requester who created it" means the creator, whatever their role.** Amir can edit a draft he created himself, just as he can submit it today. Approvers are refused only on other people's drafts, which is what the issue rules out.
- **The ownership check comes before the status check.** A non-owner gets `404` for a request in any status. Only the creator learns that their request is no longer a draft (`409`), as with submit.
- **The 409 message is `only a draft can be edited`**, matching submit's `only a draft can be submitted`.
- **Wording:** the form is `Edit request`, the buttons are `Edit` (named `Edit <title>`), `Save changes` and `Cancel`. The edit form replaces the new-request form in the same place, above the list (an open question the issue left to the planner).
- **A failed save keeps the form open** and shows the error in the existing alert, as a failed create does.
