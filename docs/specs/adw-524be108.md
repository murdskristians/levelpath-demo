# Edit a draft purchase request

> Issue #49: Intent: Edit a draft purchase request before submitting it · Type: feature · Intent: none

## Summary

- A new route `PUT /purchase-requests/:id` replaces every field of the caller's own draft.
- Only the requester who created it can edit it, and only while it is a draft. Everyone else gets the same 404 as for an unseen id.
- "My requests" shows an Edit button on each draft. It opens the new-request form pre-filled, with Save and Cancel.
- The shared Zod schema and the contract doc cover the new body. No migration.

## Context

- `apps/api/src/purchase-requests/purchase-requests.controller.ts` has `mine`, `to-decide`, create, submit and decision. `purchase-requests.service.ts` has `submit`, which looks up the row by id and `requester_id`, answers 404 if absent and 409 if it is not a draft, then updates conditionally on `status = 'draft'`. Edit follows the same pattern.
- `packages/shared/src/purchase-requests.ts` has `createPurchaseRequestSchema`, a strict object with title, amountCents, currency, supplierId, category and description.
- `apps/web/src/components/NewRequestForm.tsx` is the form (it also drives Suggest fields). `RequestList.tsx` renders the Submit button on drafts. `App.tsx` owns `formOpen` and the actions. `apps/web/src/api.ts` is the API client.
- `purchase_requests` already has RLS, a `tenant_isolation` policy and `UPDATE` granted to the app role (`db/migrations/0003`).

## Requirements

1. `PUT /purchase-requests/:id` takes a body validated by the shared schema, the same fields and rules as create. Unknown keys (`id`, `status`, `tenantId`, `requesterId`) are rejected with 400.
2. It updates title, amount, currency, supplier, category and description of the caller's own draft, sets `updated_at`, and returns `200` with the `PurchaseRequest`. The status stays `draft`. Requester, tenant, id and `created_at` don't change.
3. A non-UUID id, an unknown id, another requester's request, an approver acting on someone else's request, and another tenant's id are all `404` with the same body.
4. The caller's own request that is not a draft (submitted, approved, rejected) is `409`, like a second submit.
5. A supplier that is unknown or belongs to another tenant is `404` and changes nothing.
6. A refused edit changes nothing in the row, including `updated_at`.
7. The tenant and user come from `@CurrentUser()`. All data access is through `withTenant`.
8. The shared package exports the edit schema and types. `docs/specs/purchase-requests-contract.md` lists the route and the shape.
9. The web client has `api.updateRequest(id, input)`.
10. In "My requests", each draft has an Edit button (accessible name `Edit <title>`) next to Submit. Other statuses have none.
11. Clicking Edit opens the same form as New request, pre-filled with the draft's values (amount shown as text, like `12.50`). The submit button is named `Save changes`, and Cancel is `Cancel`.
12. Save validates with the shared schema, calls the update, closes the form and reloads the list, which shows the new values. The draft is still a draft.
13. Cancel closes the form and sends nothing. The list is unchanged.
14. Suggest fields works in the edit form exactly as when creating.
15. An API error on save shows in the existing `ErrorAlert`.

## Acceptance criteria

1. As Alice (Acme requester), create a draft, then `PUT /purchase-requests/<id>` with all six fields changed. The response is `200`, `status` is `draft`, the fields are the new ones, `updatedAt` is later than before, and `GET /purchase-requests/mine` shows them. (API test)
2. The same PUT with `description` left out and `currency` left out gives `200`, with `description: ""` and `currency: "EUR"`, as create does. (API test)
3. A PUT by another Acme requester on Alice's draft gives `404`, and the owner-client row is unchanged. (API test)
4. A PUT by an Acme approver on Alice's draft gives `404`, and the row is unchanged. (API test)
5. A PUT by a Globex user with Alice's real id gives `404`. Its body is identical to the body for a random unknown UUID and for a non-UUID id. The row is unchanged. (API test)
6. A PUT on the caller's own submitted request gives `409`, and the row is unchanged. The same for approved and rejected. (API test)
7. A PUT with an invalid body (empty title, negative amount, bad currency, bad category, a bad supplier id, `status`, `id` or `tenantId` as extra keys) gives `400`, and the row is unchanged. (API test)
8. A PUT with a Globex supplier id on an Acme draft gives `404`, and the row is unchanged. (API test)
9. A PUT without `X-User-Id` gives `401`. (API test)
10. A PUT cannot move a row to another tenant or requester: after a valid edit the owner-client row has the same `tenant_id`, `requester_id` and `created_at`. (API test)
11. `packages/shared` tests parse a valid edit body and reject an extra key. (shared test)
12. Web: a draft in the list has a button named `Edit <title>` with the text `Edit`, and submitted, approved and rejected requests have none. (web test)
13. Web: clicking Edit shows a form with the draft's title, amount, currency, supplier, category and description filled in and a button named `Save changes`. There is no `Create request` button. (web test)
14. Web: change the title and click Save changes. The test sees `PUT /api/purchase-requests/<id>` with the full body, the form closes, the list is re-fetched and shows the new title. (web test)
15. Web: click Cancel. No PUT is sent, the form closes, and the list shows the old values. (web test)
16. Web: Save with an empty title shows the title error and sends nothing. A failed PUT (409) shows the error alert and leaves the form open. (web test)
17. Web: in the edit form, Suggest fields fills the fields, as in the create form. (web test)
18. Manual: run the app on chosen ports, as Alice click Edit on a draft, change the amount, Save. The list shows the new amount and `Draft`. Submit still works afterwards.

## Tenant isolation and security

- The update runs inside `withTenant(user.tenantId, …)`. RLS limits the rows to the tenant. The statement also filters on `requester_id = user.userId` and `status = 'draft'`.
- The id is the only thing in the URL. Tenant, requester and status can't be sent: the schema is strict and the SQL never takes them from the body.
- Not found, not yours and another tenant look the same (404), so a crafted id reveals nothing.
- Supplier ownership is enforced by the existing composite foreign key. A violation is a 404.
- `X-User-Id` is a dev stub, not authentication.

## Out of scope

- Deleting or discarding a draft, an edit history, a conflict check (the last save wins).
- Editing a submitted, approved or rejected request.
- Any migration or a change to RLS policies.
- Partial updates (PATCH).

## Assumptions

- The method is `PUT` with the full create body, since the form always sends every field. The edit schema is the create schema under another name.
- The edit rule is "the creator, while draft", so it is the same for every role. An approver can edit their own draft but not another person's, which is a 404. The issue's "approvers can't edit" is read as other people's drafts.
- The body is validated before the id is looked up (the pipe runs first), as with decision. A non-UUID id with a valid body is 404, and with an invalid body it is 400.
- The button wording is `Edit`, `Save changes` and `Cancel`.
- The edit form replaces the new-request form at the top of the section. Only one form is open at a time.
