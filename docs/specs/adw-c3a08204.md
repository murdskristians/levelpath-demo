# Edit a draft purchase request

> Issue #45: Intent: Edit a draft purchase request before submitting it · Type: feature · Intent: none (the issue is the intent)

## Summary

- A new route, `PUT /purchase-requests/:id`, lets the requester who created a draft replace its fields.
- It reuses the create body schema, so the validation is the same as creating.
- Anyone else, and any other tenant, gets the same 404 as for an unseen id. A request that is no longer a draft gets 409, as a second submit does.
- In "My requests" each draft gets an Edit button next to Submit. It opens the new-request form pre-filled, with Save changes and Cancel.
- No migration. The contract document is updated.

## Context

- `apps/api/src/purchase-requests/purchase-requests.controller.ts` has `GET mine`, `GET to-decide`, `POST`, `POST :id/submit` and `POST :id/decision`.
- `purchase-requests.service.ts`: `submit` selects the row with `requester_id = caller` and answers 404 if absent, then 409 if it is not a draft. It updates with `where status = 'draft'`, then calls `readBack`. `create` maps a key violation (a bad or other-tenant supplier) to 404.
- `packages/shared/src/purchase-requests.ts`: `createPurchaseRequestSchema` is strict (the client can't send `id`, `status`, `tenantId` or `requesterId`).
- `apps/web/src/api.ts`: `createApi(userId)` with a `call` helper that supports only GET and POST.
- `apps/web/src/App.tsx`: `Dashboard` holds `formOpen` and renders `NewRequestForm` and `RequestList`.
- `apps/web/src/components/NewRequestForm.tsx` has the form, with Suggest fields and "Create request" and "Cancel".
- `apps/web/src/components/RequestList.tsx` shows a Submit button on drafts, with the accessible name `Submit <title>`.
- `docs/specs/purchase-requests-contract.md` holds the routes table.
- Seeded Acme users: Alice (requester, `SEED.acme.requester`) and Amir (approver, `SEED.acme.approver`). There is no second Acme requester. Seeded requests `A.purchaseRequests[0]` is Alice's draft, `[1]` submitted, `[2]` approved.

## Requirements

1. `PUT /purchase-requests/:id` takes a body validated by the shared create schema. It is exported under the name `updatePurchaseRequestSchema`, with the types `UpdatePurchaseRequest` and `UpdatePurchaseRequestInput`. The create schema is not duplicated.
2. On success it replaces title, amount, currency, supplier, category and description of the caller's own draft. The status stays `draft`, `updated_at` is set to `now()`, and the response is `200 PurchaseRequest`. `id`, `status`, `requester_id`, `tenant_id` and `created_at` never change.
3. A non-UUID id, an unknown id, another tenant's id, and a request created by someone else (any role) all give the same `404 {"statusCode":404,"message":"Not Found"}`.
4. A request of the caller's own that is not a draft gives 409. The update is conditional on `status = 'draft'`, so a concurrent submit cannot be overwritten.
5. An invalid body gives 400 with `issues`, as on create. A supplier that is unknown or belongs to another tenant gives 404, as on create.
6. A refused edit writes nothing. The row, including `updated_at`, is unchanged.
7. All data access goes through `withTenant`. The tenant and the caller come only from `@CurrentUser()`. No migration.
8. Web: an Edit button shows on each draft in "My requests", next to Submit. Its accessible name is `Edit <title>`. It opens the same form as New request, pre-filled with the draft's values: description, title, category, amount (as text), currency and supplier. The form's accessible name is `Edit request`, the save button reads `Save changes` and the cancel button reads `Cancel`.
9. Save calls the update route, closes the form and reloads the list, which shows the new values. The request is still a draft. Cancel closes the form and sends nothing. Suggest fields works in the edit form exactly as in the create form.
10. The web form validates with the same shared schema. An API error shows in the existing `ErrorAlert`.
11. `docs/specs/purchase-requests-contract.md` gets the new route in its table.
12. New tests: API tests (`update.spec.ts`) and web tests (see the criteria).

## Acceptance criteria

1. As Alice (Acme requester), create a draft, then `PUT /purchase-requests/<id>` with a full valid body that has a new title, amount, currency, supplier, category and description. The answer is `200`, it parses with `purchaseRequestSchema`, it has `status: "draft"` and the new values, and the same `id`, `requester` and `createdAt`. `GET /purchase-requests/mine` shows the new values. In SQL, `updated_at > created_at`.
2. As Amir (Acme approver), `PUT` on Alice's seeded draft answers 404, and the row is unchanged.
3. As Alice, `PUT` on a Globex request id, on an unknown UUID and on `not-a-uuid` answers the same 404 (identical body). The Globex row is unchanged.
4. As Alice, `PUT` on a draft created by Amir (same tenant, another requester) answers the same 404, and the row is unchanged.
5. As Alice, `PUT` on her own submitted request and on her approved request (`A.purchaseRequests[1]` and `[2]`) answers 409, and the row (status, `updated_at` and fields) is unchanged. A draft she created, submitted, then tried to edit, also answers 409.
6. As Alice, `PUT` with an empty title, a negative amount, a lowercase currency, an invalid category, a description over 2000 characters, or an extra key (`status`, `id`, `tenantId`, `requesterId`) answers 400 with `issues`. A supplier id from Globex answers 404. In every case the row is unchanged.
7. `PUT` without `X-User-Id` answers 401.
8. After these tests, the seeded requests are unchanged (the `seededRequestsSnapshot` check used in the existing specs passes).
9. Web: render a draft in `RequestList` with `onEdit`. A button named `Edit <title>` exists for a draft only, and not for submitted, approved or rejected requests. Clicking it calls `onEdit` with the request.
10. Web: in `App`, clicking Edit opens a form named `Edit request`. Its fields hold the draft's values, and the button `Save changes` is shown. The `Create request` button is not.
11. Web: changing the title and clicking `Save changes` sends `PUT /api/purchase-requests/<id>` with the full body and `X-User-Id`, closes the form and shows the new title in the list. An invalid field shows the existing field error, and no request is sent.
12. Web: `Cancel` in the edit form closes it without any PUT, and the list still shows the old values.
13. Web: Suggest fields in the edit form fills the fields from the mocked suggestion, as it does in the create form.
14. The contract document lists `PUT /purchase-requests/:id` with its errors (400, 404, 409).

## Tenant isolation and security

- The update runs in `withTenant(user.tenantId, …)`. RLS limits it to the caller's tenant. The `requester_id = user.userId` filter in the SQL means the caller can only select and update their own rows. Another tenant's id is not found, even if it is crafted.
- The client can't set the tenant, requester, status or id: the schema is strict and the service takes them from the session and the current row.
- The supplier is checked by the existing composite foreign key, which makes an other-tenant supplier a 404.
- 404 and not 403, so the route does not reveal that a request exists.
- `X-User-Id` is still a dev stub, not authentication.

## Out of scope

- Deleting or discarding a draft.
- Edit history or an audit trail.
- A conflict check between two open forms: the last save wins.
- Editing a submitted, approved or rejected request, or resubmitting a rejected one.
- Any database change. Any change to the suggestion route.
- Partial updates (PATCH). The body is always the full create body.

## Assumptions

- The route is `PUT /purchase-requests/:id` with the full create body, because the form always sends every field. A partial `PATCH` would need a second schema.
- An approver may edit their own draft, as they can create and submit one: the rule is "the creator, while it is a draft", whatever the role. An approver editing someone else's draft gets 404, because that draft is private to its requester.
- The edit form is shown in place of the New request form, in the same position. Opening Edit closes the New request form.
- The existing `NewRequestForm` is reused with an optional `initial` request, keyed on its id so the state resets. `onCreate` keeps its name.
- A refused edit does not change `updated_at`, because nothing is updated.
