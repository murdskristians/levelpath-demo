# Edit a draft purchase request

> Issue #38: Edit a draft purchase request before submitting it · Type: feature · Intent: docs/intent/edit-draft-request.md

## Summary

- New route `PUT /purchase-requests/:id`: the requester who created a draft replaces its six fields (title, amount, currency, supplier, category, description). It stays a draft; `updatedAt` changes.
- The body is `CreatePurchaseRequest`, validated with the existing `createPurchaseRequestSchema` (strict, same rules as create). No new schema, no migration.
- Anyone else, any other tenant, an unknown or non-UUID id, or an unknown supplier gets the same `404`; a request that is no longer a draft gets `409`, as for submit. A refused edit changes nothing.
- In "My requests", every draft gets an Edit button next to Submit. It opens the same form, pre-filled, titled "Edit request", with "Save changes" and "Cancel". Suggest fields works in it.
- The contract document gets the new row and the full-replacement rule.

- **API logic:** `apps/api/src/purchase-requests/purchase-requests.service.ts`. `create` (lines 49-74) inserts inside `withTenant` and turns a composite-FK violation on the supplier (`isKeyViolation`, `apps/api/src/db/pg-errors.ts`) into a 404. `submit` (lines 77-99) is the owner-only, draft-only pattern: `isUuid` check, a select filtered by `requester_id = user.userId` (404 if none), 409 if not a draft, then a conditional `UPDATE … WHERE status = 'draft'` with `updated_at: sql<Date>\`now()\``, then `readBack`(lines 144-147) through`selectPurchaseRequests`/`toPurchaseRequest` (`purchase-request.query.ts`).
- **Shared contract:** `packages/shared/src/purchase-requests.ts`: `createPurchaseRequestSchema` (lines 37-44; strict; title trimmed 1..200, `amountCents` 0..`MAX_AMOUNT_CENTS`, `currency` default `EUR`, `supplierId` uuid, `category` enum, `description` trimmed 0..2000 default `''`), `purchaseRequestSchema` (the response). `docs/specs/purchase-requests-contract.md` lists the routes (lines 11-19) and the "404, never 403" rule (line 21).
- **Database:** `db/migrations/0003_purchase_requests.sql`: `purchase_requests` with RLS enabled and forced, the `tenant_isolation` policy (USING and WITH CHECK), `UPDATE` granted to the app role, composite FK `(tenant_id, supplier_id)` to `suppliers`, `updated_at` with no trigger. `0005` adds the `category` and `description` CHECKs. ## Requirements

1. `PUT /purchase-requests/:id` exists. It needs `X-User-Id` like every route (401 without it).
2. Its body is validated with `createPurchaseRequestSchema` from `packages/shared`, through `ZodValidationPipe`, exactly as create. An invalid body (including any extra key such as `id`, `tenantId`, `requesterId` or `status`, or no body) is a `400` with `issues`, and changes nothing.
3. The edit is a **full replacement** of the six fields: a field left out takes the schema's default (`currency` `EUR`, `description` `''`).
4. The tenant and the caller come only from `@CurrentUser()`. All reads and writes run inside `DatabaseService.withTenant(user.tenantId, …)`.
5. Only the request's own requester may edit it, whatever their role (an approver may edit a draft they created). For a non-UUID id, an unknown id, another tenant's id, or another user's request (including an approver's attempt on a requester's draft), the answer is `404 {"message":"Not Found","statusCode":404}`, byte-for-byte the same in every case.
6. A `supplierId` the caller's company doesn't have (unknown, or another tenant's) is the same `404`, and changes nothing.
7. A request of the caller that is not a draft (submitted, approved, rejected) is `409`, and changes nothing. The update is conditional on `status = 'draft'`, so a submit that lands between the check and the write can't be overwritten: that edit also gets `409`.
8. A successful edit answers `200` with the `PurchaseRequest` (parsed by `purchaseRequestSchema`): the same `id`, `status` `draft`, the same requester and `createdAt`, the new field values (trimmed), and an `updatedAt` later than before. The row in the database matches.
9. `docs/specs/purchase-requests-contract.md` gets a row for the route and a bullet stating the full-replacement rule.
10. In "My requests", every draft has an Edit button next to Submit, visible text "Edit", accessible name `Edit <title>`. Requests that are not drafts have none.
11. Edit opens the same form component, above the list, with accessible name "Edit request", pre-filled with the draft's description, title, category, amount (as `12.50`-style text), currency and supplier, with Title focused. Its submit button reads "Save changes"; Cancel reads "Cancel". The "New request" button is hidden while it is open.
12. The edit form validates with the same rules and messages as the create form, and sends nothing while a field is invalid.
13. Save sends one `PUT /api/purchase-requests/<id>` with all six fields, closes the form and re-fetches "My requests", which shows the new values with the Draft badge and the Submit and Edit buttons. A failed save (for example `409`) shows the API message in the existing alert and keeps the form open.
14. Cancel closes the form, sends nothing, and leaves the list as it was.
15. Suggest fields in the edit form behaves as in the create form (one `POST /purchase-requests/suggestion`, fills and tags fields), and a following Save sends the `PUT`.
16. The web API client gets `updateRequest(id, input)` sending `PUT` and parsing the reply with `purchaseRequestSchema`.
17. New tests: an API spec for the route (every case above), web tests for the button, the pre-filled form, save, cancel, validation, a failed save and Suggest fields, and an `api.test.ts` case for `updateRequest`. No existing test is changed except where a renamed form prop forces it (none is expected: the existing tests go through `App`).
18. `docs/LEARNING.md` gets one short entry on the edit as a full replacement with the create schema.

## Tenant isolation and security

- **RLS does the tenant check.** Every read and write of the route runs in `withTenant(user.tenantId, …)` as the non-owner app role, so `purchase_requests` rows of another tenant are invisible to the select and untouchable by the update (policy USING); the policy's WITH CHECK and the strict body (no `tenantId`) keep a row from moving tenant. No new way to the pool, no raw SQL with user input: Kysely's builder with parameters.
- **Ownership is in the query.** The select and the update both filter `requester_id = user.userId`, with the user from `@CurrentUser()`, never from the body, query or path. Another requester, an approver, or another tenant gets the same 404 as an unknown id: the response never tells them the request exists (contract line 21).
- **Supplier across tenants.** The composite FK `(tenant_id, supplier_id)` rejects another company's supplier; the `23503` is answered as the same 404 as an unknown supplier (`isKeyViolation`), so it doesn't reveal that the key exists.
- **The client can't choose what the server decides.** The strict schema rejects `id`, `tenantId`, `requesterId`, `status` and any other key; the update sets only the six fields and `updated_at`.
- **Order of checks.** The body is validated before the id is looked up, so a 400 is the same for every id and reveals nothing.
- **`X-User-Id` is a dev stub, not authentication**; nothing in this change presents it otherwise.
- **No PII in logs.** The route logs nothing new.

## Out of scope

- Deleting or discarding a draft; an edit history or audit trail; a conflict check between two open forms (last save wins).
- Editing a submitted, approved or rejected request, or resubmitting a rejected one.
- A partial update (`PATCH`) or a new update schema in `packages/shared`.
- Any migration, trigger, grant or policy change.
- Submitting from the edit form (Save keeps it a draft; Submit stays the list's button).
- Restyling the list or form beyond placing Edit next to Submit; changing the create form's wording or behaviour.
- Editing the seeded drafts in tests (they are in `seededRequestsSnapshot`).

## Assumptions

- **`PUT /purchase-requests/:id`, full replacement.** The intake says the body is the same as create with the same validation; reusing `createPurchaseRequestSchema` (with its defaults) makes the edit a full replacement, which is what `PUT` means. The web form always sends all six fields.
- **No separate `updatePurchaseRequestSchema`.** The body is identical to create's; a second name for the same schema adds nothing.
- **An approver may edit their own draft.** The rule is "only the requester who created it"; an approver who created a draft is that requester (approvers can create drafts today).
- **400 before 404/409.** `ZodValidationPipe` runs before the service, as for create and decide; a 400 does not depend on the id, so it reveals nothing. A non-draft with an invalid body therefore gets 400.
- **409 message `only a draft can be edited`**, matching submit's wording.
- **The edit form takes the create form's place, above the list.** Only one form is open at a time; clicking Edit on another draft while a form is open switches the form to that draft (fresh state, no carried-over Suggested tags).
- **Wording:** "Edit" (accessible name `Edit <title>`), form "Edit request", "Save changes", "Cancel". The intake leaves wording open as long as each name says what it does.
- **A failed save keeps the form open** with the API's message in the existing alert, so the user doesn't lose their changes.
